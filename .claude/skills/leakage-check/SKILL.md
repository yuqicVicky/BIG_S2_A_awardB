name: leakage-check
description: Use this skill before modeling, during preprocessing, during plan critique, and during inspection to detect target leakage, ID leakage, preprocessing leakage, future-information leakage, duplicate leakage, and invalid train/test separation in tabular ML workflows.
---

# Skill: leakage-check

## When to Use

This skill runs at four distinct points in the workflow. Each invocation has a different scope.

| Invocation Point | Scope | Minimum Checks Required |
|------------------|-------|------------------------|
| `plan_critique` | Audit the draft plan for structural leakage risks before any execution | Checks 1, 2, 3, 7 |
| `leakage_check` step (standalone gate) | Audit raw data and feature candidates before split | Checks 1, 2, 3, 7, 8 |
| `preprocessing` (post-split inspection) | Verify split was performed first; verify transformers fit on train only | Checks 4, 5, 6 |
| `modeling` / `evaluation` (post-fit inspection) | Verify no test data touched during training or tuning; verify metrics on held-out data | Checks 4, 6, 9 |

Run every check in the applicable set for the current invocation point. Do not skip checks because they seem unlikely to apply — the purpose of this skill is systematic verification, not intuition.

---

## Required Checks

### Check 1 — Target Variable in Feature Set

**Question:** Is the target variable (or any transformation of it) present in the feature columns used for training?

**What to look for:**
- `state.task.target_variable` appears in `state.task.feature_candidates`.
- A column with a name derived from the target (e.g., `survived_encoded`, `churn_flag`, `label_int`) appears in features.
- A column whose values are a direct function of the target (one-to-one or near-one-to-one mapping) appears in features.

**Detection method:**
- Check `feature_candidates` against `target_variable` directly (exact match).
- Check for near-perfect correlation: if any feature has point-biserial or Pearson correlation with target `> 0.95`, flag it.
- Check for derived name patterns: `<target>_encoded`, `<target>_binary`, `<target>_int`, `<target>_flag`.

**Severity:** FAIL — no exception.

---

### Check 2 — ID-Like Columns in Feature Set

**Question:** Are columns that uniquely identify rows present in the feature set?

**What to look for:**
- Any column from `state.data_profile.potential_id_columns` that appears in `state.task.feature_candidates`.
- Any column where `n_unique == n_rows` that is not the target.
- Any column named with patterns from the Suspicious Column Patterns list (Section 3, ID group).

**Detection method:**
- Cross-reference `feature_candidates` against `data_profile.potential_id_columns`.
- For each feature, check `data_profile.categorical_columns[col].n_unique` and `data_profile.n_rows`. Flag if equal.
- Check column names against ID patterns.

**Why this is leakage:** An ID column that is unique per row has no generalization value but can allow a model to memorize the training set, producing inflated training metrics that do not transfer to unseen data.

**Severity:** FAIL — no exception.

---

### Check 3 — Future-Information and Post-Outcome Variables

**Question:** Do any features contain information that would not be available at prediction time, or information that was recorded after the outcome occurred?

**What to look for:**
- Column names containing temporal or post-event patterns (see Section 3, Temporal / Post-Outcome group).
- Columns whose values are recorded after the target event (e.g., `diagnosis_after`, `treatment_result`, `post_discharge_status`).
- In time-series or event-based data: features with timestamps later than the prediction timestamp.
- A "score" or "probability" column that was clearly generated by a prior model trained on the same dataset.

**Detection method:**
- Pattern-match all feature column names against the Temporal / Post-Outcome suspicious patterns list.
- Check `data_profile.datetime_columns`: if any feature has a datetime that is after the target event datetime, flag it.
- Flag any column whose name contains `score`, `pred`, `probability`, or `proba` when a target variable also exists.

**Severity:** FAIL if a column matching a strong post-outcome pattern (`post_`, `after_`, `final_`, `diagnosis_after`, `status_after`) is in features. WARN for weaker temporal signals (column name contains `date` or `time` but no clear post-event indicator).

---

### Check 4 — Preprocessing Before Split

**Question:** Was any data transformation fitted before the train/test split was performed?

**What to look for:**
- In the execution log or plan: `fit()` or `fit_transform()` called on the full dataset before `train_test_split()`.
- `state.splits` is populated after any call to a transformer's `fit` method.
- Any transformer object in `state.transformers` that records `n_samples_seen_` greater than the training split size.

**Detection method (plan audit):**
- Scan `state.plan.approved` step order: verify `data-splitter` appears before any `feature-engineer` invocation.
- If any preprocessing step precedes the split step in the plan, flag it.

**Detection method (execution audit):**
- Check `state.execution_log`: verify timestamp of split step precedes timestamp of any transformer fit step.
- Verify `transformer.n_samples_seen_` (if available) equals `len(X_train)`, not `len(X_full)`.

**Severity:** FAIL — no exception. This is the most common and most damaging form of leakage.

---

### Check 5 — Transformer Fitted on Non-Training Data

**Question:** Were imputers, scalers, or encoders fitted on validation or test data?

**What to look for:**
- `fit_transform(X_train_val_combined)` used instead of `fit(X_train).transform(X_val)`.
- Scaler or imputer statistics (mean, median, categories) computed from the full dataset.
- Any transformer step in the plan where `inputs` includes `X_val` or `X_test` during fitting.

**Detection method:**
- Inspect `state.transformers`: each transformer must record `fitted_on: X_train`.
- If `fitted_on` is missing or `fitted_on: X_full`, flag as FAIL.
- Check plan: verify each preprocessing step's `inputs` for the fit call includes only `state.splits.X_train`.

**Severity:** FAIL — no exception. Fitting on validation or test data inflates apparent generalization.

---

### Check 6 — Feature Selection Performed Outside Training Set

**Question:** Was feature selection (variance filters, mutual information, RFE, correlation filters) performed on the full dataset or using test labels?

**What to look for:**
- Feature selection step in plan that lists `state.raw_data` or `X_full` as input (instead of `X_train` and `y_train`).
- Correlation-based feature selection that uses the full dataset's correlation matrix.
- Any step that selects features based on their correlation with `y_test` or `y_val`.

**Detection method:**
- Check `state.plan.approved` and `state.execution_log`: feature selection inputs must be `X_train` and `y_train` only, or performed entirely within cross-validation folds.
- Flag any plan step where `feature-engineer` is applied before `data-splitter`.

**Severity:** WARN if selection is correlation-based on training data only (minor risk of overfitting to train distribution). FAIL if selection used val or test labels.

---

### Check 7 — Duplicate Rows Spanning Train and Test Sets

**Question:** Are there duplicate rows that appear in both the training set and the test set, allowing the model to memorize rather than generalize?

**What to look for:**
- `state.data_profile.duplicate_count > 0` — duplicates in the raw data that survive into the split.
- After splitting, rows in `X_test` that also appear in `X_train` (exact feature-value match).

**Detection method:**
- If `data_profile.duplicate_count > 0`: flag as WARN pre-split (duplicates exist but split behavior is unknown).
- Post-split: compute `pd.merge(X_train, X_test, how='inner')`. If any rows match, flag as FAIL.
- Near-duplicates (all features identical except one) are a WARN.

**Severity:** FAIL if exact duplicates span train and test. WARN if duplicates exist in raw data but split has not yet occurred.

---

### Check 8 — Suspiciously Predictive Feature

**Question:** Does any single feature predict the target with unusually high accuracy, suggesting it encodes the target directly or indirectly?

**What to look for:**
- A single feature with AUC > 0.98 or correlation with target > 0.95.
- A feature that perfectly separates classes.
- A feature whose name or description suggests it was created from the target.

**Detection method:**
- For each feature in `feature_candidates`, compute univariate AUC (for classification) or correlation (for regression) against the target on training data only.
- Flag any feature with AUC > 0.98 (classification) or |correlation| > 0.95 (regression) as a suspected leakage column.
- Pattern-match feature name against `score_generated_from_target` and `prediction` patterns.

**Severity:** WARN with `suspected_leakage_column` type. Does not auto-FAIL — requires human review. Escalate to FAIL if the column also matches a suspicious name pattern.

---

### Check 9 — Metrics Computed on Training or Validation Data Reported as Final

**Question:** Are the final reported metrics computed on the held-out test set, or on training/validation data?

**What to look for:**
- `state.evaluation` contains metrics where `split` is `train` or `val` but labeled as final.
- Report draft refers to a metric without a `split` label.
- Model selection (choosing the best model) was performed using test set performance rather than validation set performance.

**Detection method:**
- Verify `state.evaluation`: every metric entry must have a `split` field with value `test`.
- Check `state.execution_log`: confirm the test set was only accessed in the `evaluate_test` step.
- If any metric in `state.report_draft` lacks a split label, flag it.

**Severity:** FAIL if final metrics are not on the test set. WARN if split labels are missing from the report.

## Suspicious Column Name Patterns

Column names matching these patterns must be flagged during Check 1, 2, and 3.

### Target / Label Patterns

These suggest the column may encode or derive from the outcome variable:

| Pattern | Risk | Check |
|---------|------|-------|
| `target` | Direct target encoding | 1 |
| `label` | Direct label | 1 |
| `outcome` | Direct outcome | 1 |
| `y_true` | Target alias | 1 |
| `ground_truth` | Target alias | 1 |
| `*_encoded` (when target is categorical) | Encoded target | 1 |
| `prediction` | Model output as feature | 1, 8 |
| `score_generated_from_target` | Explicit derivative | 1, 8 |
| `pred_*` | Predicted value | 1, 8 |
| `proba_*` | Predicted probability | 1, 8 |

### ID / Row-Identifier Patterns

These suggest the column uniquely identifies rows and will not generalize:

| Pattern | Risk | Check |
|---------|------|-------|
| `id`, `*_id`, `id_*` | Row identifier | 2 |
| `uuid`, `guid` | Row identifier | 2 |
| `key`, `*_key` | Row identifier | 2 |
| `index`, `row_index` | Row identifier | 2 |
| `code` (when unique per row) | Row identifier | 2 |
| `ref`, `*_ref` | Reference key | 2 |
| `serial`, `serial_*` | Serial identifier | 2 |
| `unnamed: *` | Exported index artifact | 2 |

### Temporal / Post-Outcome Patterns

These suggest information that was recorded after the prediction event:

| Pattern | Risk | Check |
|---------|------|-------|
| `future_*` | Future information | 3 |
| `post_*` | Post-event recording | 3 |
| `after_*` | Post-event recording | 3 |
| `final_*` | Final state (may be post-outcome) | 3 |
| `diagnosis_after` | Post-diagnosis | 3 |
| `status_after` | Post-event status | 3 |
| `end_*` | End-state value | 3 |
| `result_*` | Outcome result | 3 |
| `*_at_discharge` | Post-event medical | 3 |
| `*_at_followup` | Post-event medical | 3 |
| `next_*` | Next-period value | 3 |

Pattern matching is case-insensitive and applies to the full column name including underscores.

---

## High-Risk Workflow Patterns

Beyond column-level checks, flag these workflow-level patterns as high risk regardless of column names.

| Pattern | Description | Severity |
|---------|-------------|----------|
| `fit_transform` on full `X` | `preprocessor.fit_transform(df[features])` before split | FAIL |
| `StandardScaler().fit(X)` where X includes val/test | Scaler fitted on superset of train | FAIL |
| `LabelEncoder` applied to full column before split | Encodes test labels during fit | FAIL |
| Cross-validation using `X_full` + `y_full` after test set is defined | CV leaks test distribution | FAIL |
| Feature importance from full-data model used to select features, then re-fit | Selection leaks test signal | WARN |
| `df.fillna(df.mean())` before split | Mean computed from full data including test | FAIL |
| `pd.get_dummies` on full dataset before split | Encoding categories from test set | FAIL |
| `train_test_split` called after `fit_transform` in code order | Classic preprocessing-before-split | FAIL |
| Hyperparameter tuning using test set accuracy as objective | Test set used for model selection | FAIL |
| SMOTE/oversampling applied before split | Synthetic samples from test distribution | FAIL |

### Field Definitions

| Field | Type | Description |
|-------|------|-------------|
| `invocation_point` | `string` | One of: `plan_critique`, `leakage_check`, `preprocessing`, `modeling` |
| `checks_performed` | `list[int]` | Check numbers run at this invocation point |
| `leakage_risk` | `string` | `low` / `medium` / `high` — overall risk level |
| `approved` | `boolean` | `true` only if zero FAIL verdicts across all checks |
| `suspected_columns` | `list[object]` | Per-column findings with check ID and verdict |
| `failed_checks` | `list[object]` | All checks that returned FAIL; must be empty for `approved: true` |
| `warned_checks` | `list[object]` | All checks that returned WARN; does not block approval |
| `required_fixes` | `list[object]` | One entry per FAIL, with the concrete remediation action |
| `warnings` | `list[object]` | All warnings including those from `warned_checks` |

### Risk Level Mapping

| `leakage_risk` | Condition |
|----------------|-----------|
| `low` | Zero FAILs, zero WARNs |
| `medium` | Zero FAILs, one or more WARNs |
| `high` | One or more FAILs |

`approved: true` requires `leakage_risk` to be `low` or `medium`. A `high` risk always produces `approved: false`.

---

## Failure Criteria

The following conditions unconditionally produce `verdict: FAIL` and set `approved: false`. They cannot be overridden by the Orchestrator, waived by the Planner, or suppressed in the output.

| Condition | Check | Rationale |
|-----------|-------|-----------|
| Target variable appears in `feature_candidates` | 1 | Direct label leakage; model trains on the answer |
| Derived target column in `feature_candidates` (correlation > 0.95) | 1 | Indirect label leakage |
| Any column from `data_profile.potential_id_columns` in `feature_candidates` | 2 | ID memorization; no generalization |
| Any column with `n_unique == n_rows` in `feature_candidates` | 2 | Effective ID column |
| Column matching strong post-outcome pattern in `feature_candidates` (`post_*`, `after_*`, `final_*`, `diagnosis_after`, `status_after`) | 3 | Future information leakage |
| Any transformer `fit()` called before `train_test_split()` in execution order | 4 | Preprocessing leakage |
| Any transformer `fitted_on` field is not `X_train` | 5 | Val/test contamination |
| Feature selection performed using `y_val` or `y_test` | 6 | Selection leakage |
| Exact duplicate rows found in both `X_train` and `X_test` | 7 | Memorization leakage |
| Final reported metrics computed on train or val set, not test set | 9 | Invalid evaluation |
| Hyperparameter tuning objective used test set performance | 9 | Test set used for selection |

If any of these conditions is confirmed, `approved` must be `false` and the `required_fixes` list must contain a concrete remediation for each failing condition.

---

## Do Not

- **Do not assert leakage is definitively proven when evidence is only circumstantial.** A suspicious column name is a WARN, not a FAIL, unless it also has structural evidence (e.g., `n_unique == n_rows`, correlation > 0.95, or confirmed post-event recording). Use `suspected_columns` to surface ambiguity, not `failed_checks`.
- **Do not approve a run when any FAIL verdict exists.** `approved: true` requires `failed_checks` to be an empty list. No exceptions, regardless of other findings.
- **Do not auto-approve preprocessing before split.** If a transformer fit step precedes the split step in execution order, this is a FAIL. It does not matter if the transformer only saw features (not the target) — the statistical properties of the full dataset leak into the transformer.
- **Do not approve a run where the target variable appears in features.** Target-in-features is always FAIL, even if the Planner argues the column is "just for reference".
- **Do not approve a run where an ID column appears in features.** ID-in-features is always FAIL. High cardinality with `n_unique == n_rows` is the criterion; the column name alone is a WARN, not a FAIL.
- **Do not silently pass suspicious columns.** Every column flagged by the Suspicious Patterns list must appear in `suspected_columns` with its matched pattern and a human-readable reason. No finding may be discarded without a recorded verdict.
- **Do not perform leakage checks on test data.** All univariate statistics (AUC, correlation) used for Check 8 must be computed on training data only. Accessing `y_test` to compute correlations during the leakage audit is itself a form of leakage.
